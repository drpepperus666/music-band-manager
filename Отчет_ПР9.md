## 4. Индивидуальный проект

Проект «Система организации музыкальных групп» (Bandly) продолжен,
новый проект не создавался. Соответствие сущностей примеру Roomly
из методички: группа ~ помещение, участник ~ пользователь,
репетиция ~ бронирование; отмена репетиции не блокирует дату
(аналог отмененного бронирования).

- **Модели и поля:**
  - `Band` (`bands/models.py`): `name` (CharField), `foundation_date`
    (DateField), `required_instrument` (CharField),
    `is_active` (BooleanField, default True);
  - `Member` (`members/models.py`, новое приложение `members`):
    `band` (ForeignKey → Band, CASCADE, `related_name="members"`),
    `instrument`, `experience_years` (PositiveIntegerField),
    `status` (CharField, blank);
  - `Rehearsal` (`rehearsals/models.py`): `band` (ForeignKey → Band,
    PROTECT, `related_name="rehearsals"`), `rehearsal_date`
    (DateField), `participants` (PositiveIntegerField),
    `is_cancelled` (BooleanField, default False).
  - У всех моделей: `Meta.ordering`, русская `verbose_name`,
    `__str__`; у `Rehearsal` — метод `cancel()`.
- **Связи:** «многие к одному» от `Member`/`Rehearsal` к `Band`;
  прямые обращения `rehearsal.band.name`, обратные
  `band.members.all()` / `band.rehearsals.all()`;
  PROTECT у репетиций сохраняет историю при попытке удалить группу,
  CASCADE у участников — состав группы следует за группой.
- **Миграции:** `bands/migrations/0001_initial.py`,
  `members/migrations/0001_initial.py`,
  `rehearsals/migrations/0001_initial.py`; применены к `db.sqlite3`
  (`showmigrations` — `[X]`).
- **Стратегия перехода (вариант 2 из методички):** `data/bands.sqlite`
  сохранена как источник, таблицы Django созданы миграциями,
  данные перенесены скриптом `db/import_sqlite_to_orm.py`
  (`update_or_create` с сохранением `id`, порядок «группы → участники
  → репетиции», `transaction.atomic()`, `date.fromisoformat`,
  `bool()` для флагов). Итог: 2 группы, 1 участник, 1 репетиция —
  сходится с исходной базой.
- **Операции ORM (более 15 выражений, все категории из п. 2.5):**
  получение наборов (`order_by("name")`, `order_by("rehearsal_date")`)
  и объекта (`get_object_or_404`); фильтры (`is_cancelled=False`,
  `rehearsal_date=...`, `band_id=...`, `band__name__icontains`,
  `Q`-поиск по двум полям в `band_list` и `rehearsal_list`);
  `exclude(pk__in=...)` для свободных групп; сортировка из белого
  списка `SORT_FIELDS` (`date`/`band`/`participants` + `id`);
  `select_related("band")`; `annotate(F(...))` + `values()`;
  `values_list("band_id", flat=True)`; `count()`;
  `aggregate(Avg("participants"))`;
  `annotate(Count("rehearsals", filter=Q(...)))` от `Band`
  (семантика LEFT JOIN — группы без репетиций попадают в статистику
  с нулем); `Paginator.get_page` (по 5) + `{% querystring %}`.
- **Адаптированные страницы:** `/bands/` (+поиск `q`), `/bands/<id>/`
  (счетчик участников, доступность на сегодня через `exists()`),
  `/bands/available/` (валидация даты, `exclude` занятых,
  сообщение об ошибке), `/rehearsals/` (фильтры дата/группа/поиск,
  сортировка, пагинация с сохранением параметров),
  `/rehearsals/<id>/` (`select_related`), `/rehearsals/statistics/`
  (группировка + сводные `active_count`/`avg_participants`).
  Шаблоны обновлены минимально (ключи `annotate` сохранены,
  в деталке — `rehearsal.band.name`).
- **README.md** актуализирован: раздел «Слой Django ORM (ПР9)»,
  структура с `members/` и миграциями, порядок запуска.

## 5. Результат работы

- Описаны модели `Band`, `Member`, `Rehearsal`, настроены связи
  ForeignKey (`on_delete`, `related_name`).
- Созданы и применены миграции; данные перенесены без потери связей.
- Все операции с данными выполняются средствами ORM;
  прямых `sqlite3`-запросов во views не осталось
  (файлы `sql/` и `db/database.py` сохранены как реализация ПР7).
- Страницы и сценарии ПР5–ПР7 работают: списки, деталки,
  свободные группы (отмена не блокирует дату), статистика,
  фильтры/сортировка/пагинация.
